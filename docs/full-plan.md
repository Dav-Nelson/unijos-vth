## Problem Statement

The University of Jos Veterinary Teaching Hospital (VTH) in Nigeria runs on paper records.
A Unijos graduate is building a free, open-source clinic management system to digitize
three workflows: reception, clinical (with teaching sign-off chain), and billing.

Real constraints: zero budget, solo developer, Nigerian infrastructure (NEPA, slow internet,
low-end hardware), Vercel + Supabase free tiers, eventual migration to Unijos ICT.

Hospital collaboration confirmed. Dr. Avazi confirmed scope 2026-04-08.

## System Context (from clarifications, 2026-04-08)

### Clinic Structure
- **Small Animal Clinic** — highest case load, individual patients (dogs, cats, etc.)
- **Large Animal Clinic** — individual patients (sheep, goats, cattle, pigs, equine).
  Some come to VTH; some require farm visits.
- **Avian & Aquatic Clinic** — Poultry = flock (not individual). Exotic birds = individual.
  Fish = pound (not individual). Separate receptionist. Different registration form.
- **Ambulatory / Field Services** — Shares receptionist with Small/Large Animal.
  Same case numbering. Farm visits within Plateau State.
  Two-stage billing: deposit estimate paid at VTH before visit, final balance paid at VTH after return.
- **Labs**: Pathology (CBC, vaginal cytology, post mortem), Microbiology (microscopy,
  culture & sensitivity), Parasitology (faecal flotation/sedimentation).
  Students rotate 3 weeks total across all labs (few days to a week per individual lab).
  Lab sub-rotations tracked in `rotations` table (entity_type=LAB), display-only in Phase C.
  Lab case workflows deferred to Phase C+.

### Receptionist Structure
- 1 receptionist: Small Animal + Large Animal + Ambulatory
- 1 receptionist: Avian & Aquatic only (separate clinic scope)

### Patient Types

### Registration Forms

## Approach: Multi-Clinic Schema from Day 1

Patient table supports INDIVIDUAL/FLOCK/POUND from day one. Registration form renders
based on clinic type — two form configs hardcoded per `clinic_type` in the codebase
(not JSON schema config — simpler to implement, sufficient for 2 form types in v1).

One-way door. Getting this right before any real patient data exists is worth ~1 extra week.

## Phased Build Plan

### Phase A (Weeks 1–3): Multi-Clinic Reception

**What gets built:**
- Multi-clinic patient schema (INDIVIDUAL / FLOCK / POUND)
- Two registration forms (Form A: Small/Large; Form B: Avian/Aquatic)
  - Form B is **hardcoded** per `clinic_type`, not a JSON config
  - Gate Form B on obtaining the physical paper form from Avian/Aquatic reception first
- Appointment scheduling (see schema below)
- Check-in on arrival
- Case numbering: VTH-YYYY-NNNNN across all clinics
- Ambulatory case type with trip metadata
- Patient card print (B&W inkjet, CSS @media print)
- Clinic-scoped receptionist roles (2 accounts, different clinic access)
- Admin bootstrap (see below)
- Patient photo upload to Supabase Storage

**Form B provisional fields (must verify with physical form before building):**
```
Patient category:  FLOCK | INDIVIDUAL_EXOTIC | POUND
[if FLOCK]         Species, Flock size, Sick count, Avg weight (kg), Housing type
[if INDIVIDUAL]    Species (exotic bird), Age, Weight (kg), Photo
[if POUND]         Species, Pond size (m²), Estimated fish count
Owner:             Name, Phone, Address
Visit:             Chief complaint, Referral source, Vaccinated? Y/N
```

**Appointment scheduling data model:**
```
appointments
  ├── id: uuid PK
  ├── case_id: FK → cases (null until CHECKED_IN — set atomically at check-in)
  ├── owner_id: FK → owners
  ├── clinic_id: FK → clinics
  ├── scheduled_at: timestamptz
  ├── status: SCHEDULED | CHECKED_IN | IN_PROGRESS | COMPLETED | NO_SHOW | CANCELLED
  ├── assigned_vet_id: FK → users (nullable — assigned at scheduling or at check-in)
  ├── chief_complaint: text (brief note from receptionist)
  ├── created_by: FK → users (receptionist who booked)
  └── notes: text (optional)

Transitions:
  SCHEDULED → CHECKED_IN: receptionist marks arrival.
    → This action creates the `cases` row AND sets appointment.case_id in one DB transaction.
    → The case record is created here — not by the vet later.
  CHECKED_IN → IN_PROGRESS: vet opens the case (sets assigned_vet_id if not already set)
  IN_PROGRESS → COMPLETED: case closed by vet
  SCHEDULED → NO_SHOW: receptionist marks after appointment window passes
  SCHEDULED | CHECKED_IN → CANCELLED: receptionist or admin

Walk-in patients (no prior appointment):
  → Receptionist creates an appointment record directly in CHECKED_IN status
  → This simultaneously creates the case record (same transaction as above)
  → scheduled_at = now(). No SCHEDULED state is used. Walk-ins skip the queue display.
```

**Owner deduplication:**
- `owners.phone` has a UNIQUE constraint in the database
- Receptionist UI shows a "search by phone" step before the "new owner" form
- If phone matches: use existing owner, link new case to them
- No merge tool in Phase A. Duplicates created by workaround (e.g., typo in phone) are
  resolved manually by admin in the database for v1.

**Admin bootstrap:**
- Seed script creates one super-admin account (email + temporary password printed to console)
- Admin is forced to change password on first login (Next.js middleware enforces this)
- Admin creates all other user accounts via admin panel
- Receptionist accounts: admin sets `clinic_id` in Supabase `app_metadata` at creation
- No self-registration — all accounts are admin-provisioned

**Photo storage (Supabase Storage):**
- INDIVIDUAL patients: one **optional** photo stored in Supabase Storage bucket `patient-photos`
  (`photo_url` is nullable — registration completes without a photo)
- Supabase free tier: 1GB storage. At ~200KB/photo, supports ~5,000 individual animal photos.
- If 1GB is approached: compress to 200KB max client-side before upload (use browser Canvas API)
- File format: JPEG only. Max upload: 5MB (rejected with user-friendly error if exceeded)
- Phase A milestone: warn admin when storage exceeds 80% of 1GB (~819MB).
  Metric: call Supabase Storage Management API (`GET /storage/v1/bucket/patient-photos`
  returns `size` in bytes). Called once daily via Vercel cron; result cached in a
  `system_stats` table. Admin dashboard shows current usage bar.

**Ambulatory cases:**
- `case_type: IN_CLINIC | AMBULATORY` on the `cases` table (Phase A schema from day 1)
- AMBULATORY cases also create an `ambulatory_trips` record
- `travel_fee` is required at case creation — must be entered before the trip is created
  (corrected 2026-04-09: was previously "set at return", now set upfront for Stage 1 estimate)
- Phase A only creates the case + trip record. The full two-stage billing invoice is Phase B.
- Phase A does NOT create invoices. The receptionist creates the estimate in Phase B UI.

### Phase C (Weeks 4–8): Clinical + Teaching Workflows

**What gets built:**
- Full role set: Student, Intern, Resident Vet, Lecturer, Consultant, Professor, Pharmacist
- Clinical record lifecycle: DRAFT → PENDING_REVIEW → LOCKED (+ REJECTED back to DRAFT)
- Rotation scheduling (admin UI)
- Drug formulary management (Pharmacist UI)
- Supervising vet approval queue
- Case assignment to students
- Anonymized case export for teaching
- Grand rounds mode
- Case research tagging

**Clinical lifecycle detail:**
```
DRAFT
  └─ Student/Intern creates note. Auto-saved to localStorage every 30s.
  └─ On network loss: warning banner "Saved locally — sync when connection restores."
  └─ On reconnect: client FIRST fetches record status from server.
     If status = LOCKED: show "This record was approved while you were offline.
     Your draft cannot be saved." Discard local draft. Do NOT attempt a write.
     (Avoids relying on DB rejection as conflict signal — explicit status check first.)

PENDING_REVIEW
  └─ Student submits. Supervisor sees in approval queue.
  └─ Supervisor approves OR rejects with rejection_note.

REJECTED
  └─ Returns to DRAFT. rejection_note visible to student.
  └─ Rejection is audit-logged (never deleted).

PENDING_REVIEW → LOCKED (atomic, same DB transaction — no APPROVED stored state)
  └─ "Approved" is the name of the event, not a stored status value.
     The record goes PENDING_REVIEW → LOCKED. APPROVED does not exist as a DB status.
  └─ approval_record created: { approved_by_vet_id, approved_at, approval_note, record_hash }
  └─ record_hash = SHA-256(JSON.stringify({
       chief_complaint, history, examination_findings, diagnosis,
       treatment_plan, prescriptions, approved_by_vet_id, approved_at
     })) — field set fixed at approval time, not extensible.
  └─ Hash validates DB record integrity at export time. Does NOT protect the generated
     PDF after it leaves the server. Full PDF signing is Phase C+ scope.
  └─ Record is read-only. Only admin can amend; amendment creates a new version record,
     original preserved.
```

**Supervisor approval scope:**
- Resident/Lecturer: can approve ONLY cases from their own clinic
- Consultant/Professor: can approve cases across all clinics
- Approval queue shows: pending cases from their clinic scope, sorted by waiting time

**Rotation scheduling (corrected 2026-04-09):**

Semester cycle: ~12 weeks total
  Small Animal Clinic:   3 weeks (formal block)
  Large Animal Clinic:   3 weeks (formal block)
  Avian & Aquatic:       3 weeks (formal block)
  All Labs combined:     3 weeks total (few days to a week per individual lab)

Schema: one `rotations` table, two types:
  entity_type=CLINIC — formal 3-week blocks. Drives RLS case access.
  entity_type=LAB    — lab sub-rotations. Display-only, no case access (labs deferred to Phase C+).

```
rotations
  id: uuid PK
  student_id: FK → users
  entity_id: uuid  (FK → clinics if CLINIC, FK → labs if LAB)
  entity_type: CLINIC | LAB
  start_date: date
  end_date: date
  semester: text  (e.g. '2026-SEM1')
  created_by: FK → users (admin)
```

Behavior:
- Admin assigns students at the start of each 3-week block (not daily)
- Student sees ONLY cases from their currently assigned clinic (RLS enforced)
- After rotation ends (end_date passes): read-only access to prior cases
- Admin needs a weekly schedule view: GET /api/rotations/schedule?week=YYYY-WW
  Shows all CLINIC + LAB rotations for that week, across all clinics
  Admin role (clinic_id: null) bypasses clinic-scoped RLS for this view
- No bulk import in Phase C — admin enters first batch manually from semester schedule
- Required index: idx_rotations_student_dates ON rotations(student_id, start_date, end_date)
- Required index: idx_rotations_entity ON rotations(entity_id, entity_type, start_date, end_date)

RLS policy (CLINIC type only):
  EXISTS (
    SELECT 1 FROM rotations
    WHERE rotations.student_id = auth.uid()
      AND rotations.entity_id = cases.clinic_id
      AND rotations.entity_type = 'CLINIC'
      AND NOW() BETWEEN rotations.start_date AND rotations.end_date
  )

Critical boundary test: student access on end_date (valid) and end_date+1 (read-only).
Lab sub-rotations (entity_type=LAB) do NOT satisfy this policy — display-only.

**Drug formulary:**
- Pharmacist role: can add/update drugs, mark drugs as deprecated (soft delete)
- Drug record: { name, generic_name, form (tablet/injection/liquid), unit, is_deprecated }
- Seeded from VTH pharmacy formulary by Pharmacist user at go-live (manual data entry via UI)
- No CSV import in Phase C — manual entry sufficient for initial formulary

**Anonymized export:**
- Authenticated route: `/api/cases/[id]/export-teaching`
- Logged to `export_audit_log` table: { exported_by (user_id), case_id, exported_at }
  Audit log readable by Admin only. Used for tracking who shared which cases.
- Strips: owner name, phone, address → replaced with "Owner [A]", "Phone [REDACTED]"
- Hash validated against `record_hash` before export (DB tamper check).
  Note: hash validates the DB record, NOT the generated PDF file after it leaves the server.
- Output: PDF via react-pdf (preferred over Puppeteer — no headless Chrome on Vercel free tier)
- Pagination (for Phase C+ bulk teaching export, not single-case export):
  Page size: **10 cases per PDF** (not 25 — Vercel free tier 10s limit; 10 is safely under it).
  Cursor: approved_at + case_id (stable, no drift on inserts).
  UI: "Download batch 1 of N" buttons. Each button triggers a separate paginated request.

**Grand rounds mode:**
- URL: `/cases/[id]/grand-rounds`
- Access control: same RLS as standard case view. Clinic-scoped access applies.
  Roles that can read cases (and thus access grand rounds): Student through Professor, Admin.
  Receptionists and Pharmacists cannot access clinical case pages at all.
- Requires authenticated session. If session expires mid-presentation: redirect to login
  page (standard Next.js behavior). Presenter logs in before the session starts.
- Shows: clinical details, diagnosis, treatment, photos. No owner PII, no edit buttons,
  no sidebar navigation.

**Case research tagging:**
- Single boolean field on clinical_records: `flagged_for_research: boolean, default false`
- Set by Lecturer/Consultant/Professor only (not students)
- No tag UI beyond this flag in Phase C. Phase C+ adds research filter/export.

**Lab workflow (Phase C+):**
- Deferred. Build after clinical workflow is live and battle-tested.
- Pathology, Microbiology, Parasitology each have distinct result formats — need real
  lab staff input before building the result schema.

### Phase B (Weeks 9–12): Billing

**What gets built:**
- Fee schedule: clinic_type dimension (Small/Large rates vs Avian/Aquatic rates)
- Invoice generation per visit (standard + ambulatory two-stage)
- Payment recording (cash, bank transfer)
- Receipt printing (deposit receipt + final receipt for ambulatory)
- Billing reports for admin

**Standard invoice lifecycle:**
```
PENDING → PAID
```

**Ambulatory invoice lifecycle (corrected 2026-04-09 — two-stage deposit model):**
```
ESTIMATED → DEPOSIT_PAID → VISIT_COMPLETED → FINAL_INVOICE → FULLY_PAID

Stage 1 (before farm visit, at VTH):
  1. Receptionist creates ambulatory case + enters travel_fee (required, NOT nullable)
  2. Receptionist creates estimate: estimated_total includes travel_fee + estimated treatments
  3. Client pays deposit (receptionist enters deposit_amount manually)
     CHECK: deposit_amount <= estimated_total
  4. Deposit receipt printed (payments row, type=DEPOSIT, unique receipt_number)
  5. Status: ESTIMATED → DEPOSIT_PAID
  6. Team travels to farm

Stage 2 (after farm visit, back at VTH):
  1. Receptionist sets ambulatory_trips.return_datetime
  2. Status: DEPOSIT_PAID → VISIT_COMPLETED
  3. Receptionist updates invoice with actual charges → FINAL_INVOICE
     final_total NOT NULL constraint enforced when status=FINAL_INVOICE (DB trigger)
  4. Client pays remaining balance: final_total - deposit_amount_already_paid
  5. Final receipt printed (payments row, type=FINAL, unique receipt_number)
  6. Status: FINAL_INVOICE → FULLY_PAID
```

**Invoice + payments schema:**
```
invoices
  id: uuid PK
  case_id: FK → cases
  invoice_type: AMBULATORY | STANDARD
  status: PENDING | PAID                        (standard)
         | ESTIMATED | DEPOSIT_PAID | VISIT_COMPLETED
         | FINAL_INVOICE | FULLY_PAID           (ambulatory)
  estimated_total: numeric (ambulatory only)
  final_total: numeric (null until FINAL_INVOICE; NOT NULL enforced by DB trigger)
  created_by: FK → users
  created_at: timestamptz

payments
  id: uuid PK
  invoice_id: FK → invoices
  payment_type: DEPOSIT | FINAL | FULL
  amount: numeric
  method: CASH | BANK_TRANSFER
  recorded_by: FK → users
  paid_at: timestamptz
  receipt_number: text UNIQUE

Constraints:
  CHECK: deposit_amount <= estimated_total (enforced in application + payments.amount CHECK)
  UNIQUE per invoice: at most one DEPOSIT payment, at most one FINAL payment
  DB trigger: validates status transitions (invalid transitions raise exception)
  Valid ambulatory transitions only:
    ESTIMATED → DEPOSIT_PAID
    DEPOSIT_PAID → VISIT_COMPLETED
    VISIT_COMPLETED → FINAL_INVOICE
    FINAL_INVOICE → FULLY_PAID
```

**travel_fee timing correction (from 2026-04-09):**
- `ambulatory_trips.travel_fee` is set at estimate creation (Stage 1), NOT on return.
- Required field — ambulatory estimate cannot be created without it.
- Included in `estimated_total`. After that, it's a fixed historical value on the trip record.

## Architecture: Key Decisions

### Patient Polymorphism
```
cases
  ├── id: uuid PK
  ├── case_number: text UNIQUE (VTH-YYYY-NNNNN)
  ├── patient_type: INDIVIDUAL | FLOCK | POUND
  ├── case_type: IN_CLINIC | AMBULATORY
  ├── clinic_id: FK → clinics
  ├── owner_id: FK → owners
  ├── status: OPEN | CLOSED
  └── created_at: timestamptz

individual_patients (1:1 with cases where patient_type = INDIVIDUAL)
  └── species, breed, age_months, weight_kg, photo_url

flock_patients (1:1 with cases where patient_type = FLOCK)
  └── species, flock_size, sick_count, avg_weight_kg, housing_type

pound_patients (1:1 with cases where patient_type = POUND)
  └── species, pond_size_m2, fish_count_estimate

ambulatory_trips (1:1 with cases where case_type = AMBULATORY)
  ├── farm_location: text
  ├── departure_datetime: timestamptz
  ├── return_datetime: timestamptz (null until returned)
  └── travel_fee: numeric NOT NULL  ← set at estimate creation (Stage 1), BEFORE farm visit
                                      Required — ambulatory case cannot be created without it.
                                      Included in estimated_total on invoice.
```

### Schema Constraints (must be in migrations)
```sql
-- Owner deduplication
ALTER TABLE owners ADD CONSTRAINT owners_phone_unique UNIQUE (phone);

-- Flock validation
ALTER TABLE flock_patients ADD CONSTRAINT flock_size_positive CHECK (flock_size >= 1);
ALTER TABLE flock_patients ADD CONSTRAINT sick_count_valid CHECK (sick_count >= 0 AND sick_count <= flock_size);

-- Prevent double-approval race condition
ALTER TABLE approval_records ADD CONSTRAINT one_approval_per_record UNIQUE (clinical_record_id);
```

### Clinic-Scoped Access (Supabase RLS via JWT app_metadata)
```
JWT app_metadata (set by admin at user creation):
  { "clinic_id": "uuid", "role": "RECEPTIONIST" }
  { "clinic_id": null, "role": "ADMIN" }  -- admin sees all clinics

RLS macro: (auth.jwt() -> 'app_metadata' ->> 'clinic_id')::uuid

Policies:
  Receptionist:        INSERT/SELECT cases WHERE clinic_id = JWT clinic_id
  Student/Intern:      SELECT cases WHERE student_id IN active rotation OR case_assignments
  Resident/Lecturer:   SELECT cases WHERE clinic_id = JWT clinic_id
  Consultant/Professor/Admin: SELECT all cases

Required indexes:
  CREATE INDEX idx_rotations_student_dates ON rotations (student_id, start_date, end_date);
  CREATE INDEX idx_case_assignments_student ON case_assignments (student_id);
  CREATE INDEX idx_cases_clinic ON cases (clinic_id);
```

### Clinical Record Lifecycle
```
                     ┌─────────────────────────────┐
                     ▼                             │
DRAFT ──────── PENDING_REVIEW ──── REJECTED ───────┘
                     │
                     │  (single atomic DB transaction — no intermediate APPROVED state)
                     ▼
                   LOCKED ◄── record_hash set here (SHA-256 of fixed field set)
                              approval_record created here
                              [APPROVED is the event name, not a stored status]
```

### Scheduled Jobs (no pg_cron — not available on Supabase free tier)
```
pg_cron is NOT available on Supabase free tier. Use instead:
  Vercel Cron Job (vercel.json cron field) → calls a Supabase Edge Function

Example: nightly rotation status update (ACTIVE → COMPLETED when end_date passed)
  vercel.json: { "crons": [{ "path": "/api/cron/update-rotations", "schedule": "0 0 * * *" }] }
  → /api/cron/update-rotations: protected by Authorization header check
  → Secret stored as CRON_SECRET env var in Vercel dashboard
  → Endpoint checks: if (req.headers.authorization !== `Bearer ${process.env.CRON_SECRET}`) return 401
  → If secret leaks: rotate via Vercel dashboard → redeploy

Bulk exports (anonymized case export, billing reports):
  Strategy: paginated cursor-based API (not streaming, not job queue)
  No background jobs in Phase C — export runs synchronously within Vercel's 10s limit
  At >50 cases: export is split into pages; user downloads page by page
  Phase C+ can upgrade to Edge Function streaming if needed
```

## Implementation Patterns (locked in /plan-eng-review, 2026-04-08)

### Case Number Generation
```sql
-- Atomic, race-condition-free case number generation
CREATE TABLE case_number_sequences (
  year INT PRIMARY KEY,
  next_val INT NOT NULL DEFAULT 1
);

CREATE OR REPLACE FUNCTION generate_case_number()
RETURNS TEXT AS $$
DECLARE
  current_year INT := EXTRACT(YEAR FROM NOW());
  seq_val INT;
BEGIN
  INSERT INTO case_number_sequences (year, next_val)
  VALUES (current_year, 1)
  ON CONFLICT (year) DO UPDATE
    SET next_val = case_number_sequences.next_val + 1
  RETURNING next_val INTO seq_val;

  RETURN 'VTH-' || current_year || '-' || LPAD(seq_val::TEXT, 5, '0');
END;
$$ LANGUAGE plpgsql;
-- Called at CHECKED_IN transition (case creation), not at appointment scheduling.
```

### Force Password Change
```
users table additions:
  must_change_password BOOLEAN NOT NULL DEFAULT FALSE

Seed script sets must_change_password = TRUE for the initial admin account.

Next.js middleware (middleware.ts):
  On every authenticated request:
  1. Read must_change_password from users table (server-side)
  2. If TRUE and request path != /change-password: redirect to /change-password
  3. /change-password route: updates password via Supabase Auth API + sets
     must_change_password = FALSE

Admin panel can also set must_change_password = TRUE for any user (e.g. after
a security incident or manual password reset).
```

### Student RLS Policy (Phase C)
```sql
-- Allow students to read cases where they have an active rotation
-- Applied to: clinical_records, case_assignments, appointments (Phase C)
CREATE POLICY student_active_rotation ON cases
  FOR SELECT
  USING (
    (auth.jwt() -> 'app_metadata' ->> 'role') = 'STUDENT'
    AND EXISTS (
      SELECT 1 FROM rotations
      WHERE rotations.student_id = auth.uid()
        AND rotations.clinic_id = cases.clinic_id
```

### API Error Shape
```typescript
// All API routes return this shape on error:
type ApiError = {
  error: {
    code: string;        // machine-readable: 'OWNER_PHONE_DUPLICATE'
    message: string;     // human-readable: 'A patient with this phone already exists'
    field?: string;      // optional: 'owner_phone' (for field-level errors)
  };
};

// Standard error codes:
// OWNER_PHONE_DUPLICATE — owner.phone UNIQUE constraint violation
// INVALID_TRANSITION    — invalid appointment/record status change
// RECORD_LOCKED         — attempt to edit a LOCKED clinical record
// UNAUTHORIZED          — RLS blocked or wrong role
// VALIDATION_ERROR      — Zod schema failed (field is set)
// NOT_FOUND             — resource doesn't exist
// CRON_SECRET_INVALID   — cron endpoint called without valid secret
```

### Performance Requirements
```
Appointment list query: MUST use a single JOIN, never N+1.
  Required shape:
  SELECT
    appointments.*,
    owners.name AS owner_name,
    owners.phone AS owner_phone,
    COALESCE(individual_patients.species, flock_patients.species, pound_patients.species)
      AS patient_species,
    cases.case_number
  FROM appointments
  LEFT JOIN owners ON appointments.owner_id = owners.id
  LEFT JOIN cases ON appointments.case_id = cases.id
  LEFT JOIN individual_patients ON cases.id = individual_patients.case_id
  LEFT JOIN flock_patients ON cases.id = flock_patients.case_id
  LEFT JOIN pound_patients ON cases.id = pound_patients.case_id
  WHERE appointments.clinic_id = $clinic_id
    AND appointments.scheduled_at::date = CURRENT_DATE
  ORDER BY appointments.scheduled_at ASC;

PDF export: max 10 cases per PDF (Vercel 10s timeout constraint).
  Error handling (CRITICAL GAP — must implement):
    try { const pdf = await renderPDF(cases) } catch (e) {
      return NextResponse.json({
        error: { code: 'EXPORT_TIMEOUT', message: 'Export took too long. Try a smaller batch.' }
      }, { status: 500 })
    }

Photo upload: show progress indicator during upload (not silent).
  Error handling (CRITICAL GAP — must implement):
  - Use Supabase Storage JS onUploadProgress callback for progress bar
  - 30s client-side timeout: if no completion after 30s, show "Upload timed out.
    Check your connection and try again." with retry button
  - NEPA context: Nigerian power interruptions mid-upload are common. Never leave
    user staring at a silent spinner. Always offer a clear retry path.
```

## ORM Decision (overrides design doc)

**USE: Supabase JS client only. Do NOT use Prisma for queries.**

The design doc listed Prisma. This is overridden. Reason: Prisma uses a service role
connection that bypasses Supabase RLS. All clinic-scoped access enforcement would rely
solely on application-level checks — a missed check = data leak.

The Supabase JS client (`createServerClient` from `@supabase/ssr`) respects RLS natively
on every query. This is the correct pattern for a system where access control is safety-critical.

Schema management: SQL migration files in `supabase/migrations/` (committed to git).
TypeScript types: auto-generated from schema via `supabase gen types typescript`.
